CAPNICo is installed in {{ .Values.namespace }}.

Check it:

  kubectl -n {{ .Values.namespace }} rollout status deployment/controller-manager
  kubectl get crd | grep nico
{{- if .Values.credentials.create }}
  kubectl -n {{ .Values.namespace }} get secret {{ .Values.credentials.name }}
{{- end }}

All four of nicoclusters, nicoclustertemplates, nicomachines and
nicomachinetemplates should be established.

{{- if not .Values.credentials.create }}

NOTE: credentials.create is off, so CAPNICo has nothing to authenticate to the
NICo API with. Create the Secret yourself in {{ .Values.namespace }}:

  kubectl create secret generic {{ .Values.credentials.name }} -n {{ .Values.namespace }} \
    --from-literal=endpoint=<nico-api-base-url> \
    --from-literal=orgID=<org> \
    --from-literal=apiName=<api> \
    --from-literal=token=<token>
{{- end }}

Once a site is registered, `nvkectl get providers` reports nico as CONFIGURED.
That is a narrower claim than it looks: it means the CRDs are established, the
controller is running and a credentials Secret is present. It does NOT check
that Cluster API is installed, that the credentials work, or that the backend
answers. The CREDENTIALS column reports that separately.

Before creating anything, check that the instance types have allocations. An
instance type with no allocation looks healthy and provisions nothing, and
machines retry forever in InstanceTypeUnavailable.
